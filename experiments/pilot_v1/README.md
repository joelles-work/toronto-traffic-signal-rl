# Constrained DQN/PPO pilot

This experiment freezes the current TCS379 model and the previously saved train/dev split. It is an initial training pilot, not the final research comparison. Its test periods remain sealed.

## Fixed inputs and controller constraints

`experiment.json` records the budget, seeds, architectures, reward, observations, action space, and SHA-256 hashes of frozen input copies in `assets/`. `implementation.json` records the Python source hashes at training launch. Modifying those frozen inputs causes verification to fail.

Training uses June 19, 2024, 15:00–17:00 (6,716 vehicles, 810 pedestrians). Development uses 17:00–18:00 (3,594 vehicles, 518 pedestrians). Only train and dev can be generated by the RL demand code; test files are not copied into this experiment.

Every decision covers one 120-second cycle. Both algorithms choose one of five east–west WALK allocations: 7, 19, 25, 31, or 32 seconds. North–south WALK receives the complementary allocation, totaling 39 seconds. Both WALK intervals remain at least 7 seconds. The 31/8 allocation reproduces the PM baseline. Stage order, protected-left advance, yellow, all-red, and 22/34-second pedestrian clearances remain fixed. No action can skip a phase or interrupt a crossing stage.

The observation contains per-leg approach vehicle count, queue, pending insertions, stopped pedestrians, maximum pedestrian wait, and the previous allocation. Scaling is fixed in code; no normalization statistics are fitted on dev. The reward penalizes queues, pending insertions, and waiting pedestrians equally per road user, sampled every five simulated seconds.

## Why the custom environment

The installed SUMO-RL default controller rebuilds the green/yellow sequence and allows switching between its extracted green phases. This does not preserve this site's complete walk/clearance/all-red program. The custom Gymnasium environment therefore uses SUMO's TraCI-compatible libsumo API, with Stable-Baselines3 DQN/PPO. SUMO-RL remains installed as part of the requested stack, but its default phase-switching controller is not used in this pilot.

The 600-state action audit exercises all five legal actions over complete cycles. The Gymnasium/SB3 integration check and fixed-time parity check are recorded in `checks/smoke.json`. Source-aligned geometry, lane permissions, initial queues, transit operations, walking assumptions, and historical 2024 fidelity still require calibration.

## Training and evaluation

Each algorithm is allocated 2,048 cycle decisions for each of three training seeds: 101, 202, 303. Both use a 64×64 MLP and one preset hyperparameter configuration. Training demand realizations change between episodes and are paired by training seed across algorithms. This pilot performs no architecture or reward search. The documented fixed-time baseline likewise has one preset configuration. Future tuned fixed-time controls would be additional baselines, not replacements for the documented City plan.

Each last checkpoint is evaluated deterministically on the same five dev realizations: 11, 22, 33, 44, 55. Delay metrics include vehicle timeLoss, departure delay, their sum, and pedestrian walk timeLoss. Completion, collisions, teleports, and emergency braking are retained. A controller with unfinished demand is not ranked by an all-demand mean computed from only its completed trips.

`training/*/progress.json` provides current progress; `completed.json` and `model.zip` indicate a completed training run. `dev_summary.json` is written after the complete matched comparison. Training metrics and model artifacts are saved to W&B offline records; hosted run links require later synchronization to the user's account.

No dev result is used to change architecture or training duration during this frozen pilot. The comparison may inform the next development experiment. Test performance must not be measured until a final model/configuration is frozen.

## Commands

Run from the project root with `.venv/Scripts/python.exe`:

```text
python -m rl.smoke
python -m rl.train
python -m rl.compare
```

The training command skips completed checkpoints. It does not resume partially trained models automatically. Rerunning a failed training run starts its frozen training budget again and retains any failure record. Libsumo uses one simulator per process; separate processes are required for concurrent instances. The GUI remains usable through `Open_SUMO_Intersection.cmd`; training runs headlessly and does not overwrite that drawing.
